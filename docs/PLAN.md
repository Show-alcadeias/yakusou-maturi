# 制作計画 — 薬草祭りの遭難者

## Phase 1：調査と設計（実装前）
- 対象リポジトリは空。既存コード・AGENTS.mdなし。Linux実行環境のGodotは4.6.3。
- 公式Godot 4.7.2 stableを作業領域に取得し、公式SHA512一覧との一致を確認。制作・検証を4.7.2に固定する。
- Dialogue Manager（以下DM）v4.2.0、タグのコミット `bbf9d2a5f6a9eaa276310eea8b1379a936239d2e` を採用。公式READMEはGodot 4.6以上、MITライセンスを明記。
- 調査元・導入手順・ライセンスは `DEPENDENCIES.md` に集約する。

## MVPの範囲
日本語の初稿、タイトル、11イベント、3探索地点、条件付き本文・選択肢、必ず成立する救出と帰還、救出経過と薬草成果の複合結末。1周は約5〜10分。画像・音声なしでも完結する。

## 実装順序
1. 設計4文書と依存関係記録を作成し、下記の自己レビューを完了する。
2. Godotプロジェクトと固定版DM、日本語フォントを導入。
3. GameState → GameFlow → DMシナリオ → UI →任意接続のMedia Adapter。
4. イベント開始地点の1枠セーブ・ロード。会話途中の行番号は保存しない。
5. DM実物を通すヘッドレステスト。条件の真偽・全経路・結末・保存破損を検証。
6. GUIの日本語描画・入力・小窓表示を確認。可能ならWeb書き出しも確認する。
7. 計画との差分と検証結果を `IMPLEMENTATION_REVIEW.md` に記録し、READMEを整える。
8. 開発ブランチにコミットして保存。リモートにpushし、比較元が存在すればPRを作る。mainへマージしない。

## 制作前自己レビュー
- DMのみが本文・条件式を解釈する。独自DSLや代替会話エンジンは作らない。
- 探索は訪問済みの選択肢を隠し、3地点終了後は発見へ。常時「捜索を進める」を残し、必須アイテムによる詰みを作らない。
- 条件付き応答はv4の `[if 条件 /]`。テキスト照合だけでなく実行時 `is_allowed` を両側から検証する。
- 発見以降の救助手順は最低1つ常時可能。レオの専門知識で調合・薬草評価を描き、野外判断の誤りと区別する。
- セーブはイベント開始前の状態とイベントIDを一緒に記録。ロード時の変数部分更新は禁止し、全体の妥当性確認後に反映。
- UIはスクロール可能な本文・選択肢、折り返し、フォーカス移動を備える。
- メディア接続は通知signalのみ。応答待ちや必須プラグインを増やさない。
